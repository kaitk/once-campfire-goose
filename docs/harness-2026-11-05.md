# Shared harness run on a Ryzen 7 5800X3D (November 5, 2026)

Goose against Rails, Rust and Jai in
[basecamp/once-campfire-verification](https://github.com/basecamp/once-campfire-verification),
the shared harness, with Goose added as an optional `goose` app and Jai from its open PR,
[basecamp/once-campfire-verification#11](https://github.com/basecamp/once-campfire-verification/pull/11),
merged locally for this run only. Every response was checked against its route contract and
every acknowledged post was audited against the database; the harness stops a run at the first
invalid response or failed audit. The harness wrote the JSON files in
[`harness-2026-11-05/`](harness-2026-11-05/) (see [JSON](#json)). The
[November 2](harness-2026-11-02.md) and [November 3](harness-2026-11-03.md) runs measured Goose
and Rust only, on another host, so their numbers don't compare with these.

## Host

An AMD Ryzen 7 5800X3D (8 cores, 16 threads) running **WSL2 on Windows 11 Pro**, not bare-metal
Linux: Ubuntu 26.04.1 with kernel 6.18.54.1-microsoft-standard-WSL2, 15.6 GiB of memory visible to
WSL, and Docker Engine 29.1.3 inside WSL. The apps ran on CPUs 8–11 (physical cores 4–5) and the
load generator on 12–15 (cores 6–7), so they shared no SMT siblings. WSL exposes no temperature
or clock sensors, so throttling couldn't be checked. The load average stayed at about 5–7, the
eight pinned CPUs of the benchmark itself.

## The load generator limits Goose and Jai on reads

The load generator had 4 CPUs. During every Goose and Jai page route it used 385–386% of its
400% (370–380% in the run with the writer); during Rust's it used 83–95%, and during Rails'
15–21%. So:

- Goose vs Jai on the page routes (0.95–1.04×) is the client's ceiling, and doesn't show which
  server is faster.
- Goose vs Rust and Goose vs Rails on the page routes are lower bounds.

Posting isn't affected: the load generator used 44% of its CPU there for Goose and 55% for Jai,
so those rows, Goose's 1.26× over Jai and 1.74× over Rust, are bound by the servers.

With a load generator that isn't saturated ([below](#reads-with-a-wider-load-generator)), Goose
reads 1.02–1.08× as fast as Jai.

## Memory

### Per process

Sampled once a second from `/proc` during the run without the writer, from PID 1 of each
container. Ranges are over the three rounds; MiB:

| App | Idle after start, VmRSS | Steady under reads, median VmRSS (anonymous) | Peak VmHWM |
|---|---:|---:|---:|
| Goose | 22.6–23.1 | 31.4–31.7 (14.6–15.3) | **34.3–34.5** |
| Jai | 24.4–24.7 | 37.5–37.8 (16.3–16.4) | 97.1–98.1 |
| Rust | 34.3–35.2 | 42.6–42.9 (20.6–21.1) | 113.4–113.8 |

- "Steady under reads" is the median over the four page routes, whose time windows come from the
  harness log.
- Rust and Jai peak while posting, where their anonymous memory rises to about 91 and 72 MiB.
  Goose's stays near 15 MiB.
- Rust, Jai and Goose each run as one process, so these figures cover the whole app. Rails'
  PID 1 is `bin/boot`, the wrapper; its Puma workers, Redis and Resque are children of it, so the
  18.3–18.5 MiB sampled there is the wrapper alone and says nothing about Rails; see
  [per container](#per-container).
- The samples carry no container ID; they were split per process wherever VmHWM dropped by more
  than 20%. On this kernel VmHWM also dips slightly within one process, because RSS is read from
  per-CPU counters.

### Per container

A separate run of the same four apps, `bin/benchmark --apps rails,rust,jai,goose` with 2 rounds
and the same pinning ([`memory/`](harness-2026-11-05/memory/); no errors or invalid responses,
every write audit verified). Once a second, a sampler read each container's cgroup v2
`memory.current` and `memory.peak` and the `anon` and `file` lines of its `memory.stat`, so Rails'
figures cover Puma, Redis and Resque together. Idle runs from the container's start to the first
route; reads are the four page routes; posting is the 8 seconds of the post route.

Compare anonymous memory, not file memory. cgroup v2 charges a page of the page cache to the
cgroup that first reads it, and the charge stays there. In round 1 each container is the first
to read its image's files and the seed, and is charged 53–66 MiB of file pages (Rails 177 MiB).
In round 2 those pages are already cached and stay charged to round 1's container, since
removed, so the new container shows about 0.1 MiB of them. The file pages while posting are
mostly the new message and full-text index pages that container writes.

Anonymous memory in round 2, with the cache warm; medians, MiB:

| App | Idle | Under reads | While posting |
|---|---:|---:|---:|
| Rails | 305.2 | 648.1 | 888.7 |
| Rust | 13.7 | 20.7 | 90.0 |
| Jai | 4.4 | 18.6 | 77.4 |
| Goose | **8.6** | **14.8** | **16.1** |

Goose's anonymous memory barely grows while posting, where Rust's and Jai's each add 55–70 MiB,
as the per-process figures show. Rails needs about 0.65 GiB under reads and 0.9 GiB while
posting. `memory.peak`, which also counts file pages and kernel memory such as sockets and slab,
was 1,250 and 1,067 MiB for Rails in rounds 1 and 2, 206 and 146 for Rust, 203 and 138 for Jai,
and 136 and 83 for Goose.

## Seed permissions on a host that runs the harness as root

The first preflight failed: Rails' migration reported "attempt to write a readonly database". The
harness ran as root in WSL, so each run's copy of the seed belonged to root with mode 0644, while
all four images run as uid 1000; the harness's `chmod -R a+rwX` of the storage runs only once the
container is up. Docker Desktop on a Mac hides file ownership, which is why this doesn't show
there. Making `fixtures/default` (ignored by git) writable by everyone and running the benchmarks
with `umask 000` got the preflight through for all four apps, with no change to any checkout.
[basecamp/once-campfire-verification#12](https://github.com/basecamp/once-campfire-verification/pull/12)
addresses it, by making each run's copy of the seed writable before the app starts.
